# Sync Ledger

Working memory for the sync-upstream skill. Record only what changes how a sync is performed: standing decisions, watchpoint triggers, and the full-audit marker. Never record what the code or git history already shows, and never grow this into a fork feature list.

Self-cleaning rules (apply during every sync's ledger update):

- Remove a watchpoint after two consecutive syncs in which its path was untouched by upstream or merged trivially.
- Remove a standing decision when the code it governs no longer exists on `dev`, or upstream ships the change named in its revisit condition (then re-decide with the user).
- Update the audit marker after every full audit or explicit postponement.

- **Auto-settle is a master gate over a per-reason toggle** (2026-08-14, updated 2026-08-19). `effectiveSettled` takes both the fork's required `autoSettleEnabled` (global; when false nothing auto-settles, manual settle still works) and upstream's optional `autoSettleOnMerge` (merged settles only when on; closed always settles). The master gate is checked **first**, before `changeRequestAutoSettles` — but **after** the `settledOverride` checks, or an explicit manual settle would stop working. Two silent failure modes, both of which compile: passing `{state}` without `updatedAt` reverts to always-settle, and omitting `thread` does the same. Mobile passes `autoSettleEnabled: true` hardcoded in `threadListV2.ts` because the web setting is not synced; its `changeRequestByKey` maps must compare **both** `state` and `updatedAt` before deciding the map is unchanged, and `ThreadStatusIndicators.tsx` snapshot equality must compare `pr.updatedAt` — otherwise a timestamp-only update is dropped upstream of the rule. Every call site must pass both — a site omitting `autoSettleOnMerge` silently defaults it to `true` and disagrees with the rest of the app about whether a merged thread is settled (this happened to `CommandPalette.tsx` in this sync). In the web UI the merge switch is `disabled` and reads `threadAutoSettleEnabled && sidebarAutoSettleOnMerge` while the master setting is off. **Known gap, reported 2026-08-24 and deliberately not fixed in a routine sync:** the two Woke-visibility sites (`ChatView.tsx` banner, `Sidebar.tsx` pill) call `changeRequestAutoSettles` DIRECTLY, without the master gate that `effectiveSettled` applies first. With auto-settle off, a merged or closed PR therefore stays unsettled (correct) but shows no Woke indicator (inconsistent). Both sites are byte-identical across the 2026-08-24 merge, so this is fork-owned pre-existing work, not merge damage; fixing it means passing `autoSettleEnabled` into the sidebar row and is a behavior call, not merge repair. Do NOT confuse this with the rejected hardcoded terminal-state guards described in [Woke acknowledgement is a superset]. The Sidebar/ChatView Woke pill composes `hasUnseenWake(...) && !changeRequestAutoSettles(prState, autoSettleOnMerge)` — the parameterized rule replaced the old hardcoded merged/closed check, but upstream's **sticky-woke** semantics were again rejected in favour of open-clears-attention (see [Woke acknowledgement is a superset]).
