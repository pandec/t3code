# Sync Ledger

Working memory for the sync-upstream skill. Record only what changes how a sync is performed: standing decisions, watchpoint triggers, and the full-audit marker. Never record what the code or git history already shows, and never grow this into a fork feature list.

Self-cleaning rules (apply during every sync's ledger update):

- Remove a watchpoint after two consecutive syncs in which its path was untouched by upstream or merged trivially.
- Remove a standing decision when the code it governs no longer exists on `dev`, or upstream ships the change named in its revisit condition (then re-decide with the user).
- Update the audit marker after every full audit or explicit postponement.

## Standing decisions

- **`dev` runs on upstream's orchestration v2; the sync baseline is `ddcd310282`** (2026-10-04, v2 port; replaces "`dev` stops before upstream's orchestration v2"). The fork was ported onto v2 as a separate project, not a sync: `port/orchestration-v2` merged upstream `ddcd310282` with upstream winning wherever v2 replaced fork-modified code, then rebuilt the kept fork features on v2. Once the port is in `dev`, syncs resume normally and the next range starts at `ddcd310282`. The v1 runtime (`apps/server/src/orchestration/`, its decider/projector, `ProviderService`, the v1 adapters) is gone; never re-apply fork hunks for it from pre-port history (`0b14af6127`). The v1 projection tables are not: `projection_threads`, `projection_thread_messages` and `projection_thread_pull_requests` stay as the read-only source for `LegacyV1ThreadImporter`'s lazy import, and `projection_projects` is still the live project table (`ProjectRepositoryIdentityStore` joins it), so never drop or repurpose them on a sync. Dropped fork features stay dropped, including Hermes, rate-limit failover and raw rate-limit payloads, the auto-settle master switch, the `/t3-*` title/status commands, the Attention filter and the fork's volatile background-liveness registry.
- **Fork schema lives only in fork-owned tables, through the fork ledger** (2026-10-04, v2 port; replaces "Migration numbering"). `apps/server/src/persistence/ForkMigrations.ts` records fork migrations in `fork_sql_migrations` with contiguous ids 1..N; the next one takes N+1. Never add a fork file to `persistence/Migrations/` or `migrationEntries`, and never `ALTER` an upstream table: upstream rebuilds its tables (v2 moved thread state into new `orchestration_v2_*` tables), and the migrator skips every id at or below the recorded maximum, so a fork id in upstream's ledger silently masks upstream's next migration. Upstream migrations therefore land at their own ids: take `Migrations.ts` and `Migrations/` as upstream ships them and keep only the fork's two `runMigrations` hooks (see the watchpoint). Fork state on v2 rows rides optional keys in `payload_json` (next entry); anything needing its own rows gets a `fork_*` table. The one-time history repair `forkMigrationHistory.ts` runs first in `runMigrations`, before `reconcileV2PreviewMigration`: it maps a pre-port fork ledger back to upstream ids by name, moves fork-only rows (`forkOnlyMigrationNames`) out of `effect_sql_migrations`, keeps every original row in `fork_legacy_migrations`, and is a no-op on upstream-shaped ledgers. It matches names against the current upstream manifest and refuses unknown ones, so if upstream ever renames or removes a migration the pre-port fork carried, extend the repair before shipping, or a machine not yet cut over fails at startup.

Keep both sides' cases on merges; never move fork state into new upstream columns.
- **Claude Stop settles before it closes; only parent frames set the resume cursor** (2026-09-29, rebuilt on v2 2026-10-04). In `ClaudeAdapterV2.ts`, Stop interrupts, then waits up to `CLAUDE_INTERRUPT_SETTLE_GRACE` (3 s) for the turn to settle or the process to close, and finalizes the turn as interrupted only if it is still active; upstream closes at once, which leaves a first turn Claude never saved and makes its resume fail with "No conversation found". `nativeMessageCursor` advances only on parent assistant frames, because it becomes the `resumeSessionAt` boundary for rollback and fork; a late subagent frame must not move it. `CLAUDE_ABORT_TERMINAL_REASONS` also classifies the CLI's `interrupted`/`aborted_*` results as aborts. All three are compile-clean to lose; `ClaudeAdapterV2.test.ts` covers them ("Stop closes the query only after the interrupted turn settles", "a late subagent frame does not move the rollback cursor").

- **Repository identity: v2 enrichment plus a durable fork fallback** (2026-07-24, rebuilt on v2 2026-10-04). `ProjectEnrichmentService.ts` records each successful live resolution through the optional `ProjectRepositoryIdentityStore` (`fork_project_repository_identity`, keyed by project and workspace root) and falls back to it only when live resolution yields nothing, typically a deleted checkout, so repository grouping survives restarts; a row resolved at another root never applies, and without the store enrichment is upstream's.
